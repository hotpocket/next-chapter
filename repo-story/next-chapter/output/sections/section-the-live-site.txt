This is next-chapter, the public assembly repository. The site you are listening on right now is itself the feature set — a library of three audiobooks about their own making, served as static files with no backend. This chapter tours that site: what you see and hear, then the prompts that shaped each piece.

Start where the listener starts: the landing page, the file index dot h-t-m-l. Its browser title reads "Next Chapter — a trilogy about its own making." The page is nearly empty markup — a single app container, the player script, then one inline call that hands the player the entire library as data. Inlined there is an array of three books: landry-ui, then repo-story, then next-chapter itself. Every book credits the same narrator, Brandon Landry, and every chapter title carries a "Chapter N" prefix. Across the three books there are sixteen chapters and sixteen matching summary tracks, about four and a half hours of audio in total.

That the library holds three books, and in that order, is the product of two scoping prompts. The kernel is verbatim from the July twentieth foundation session, prompt twenty-eight: "the purpose of this project is to create the github page that is the interface to the audio books that talks about the repositories... i want there to be the audiobook for the landry ui repository and the repo story repository." That fixed the site as a library of self-narrating books — at first, two. The third arrived the next day, in the July twenty-first vendored session, prompt twenty-one: "I want to add one more repo to the ones that will appear on the project page, this one: next-chapter. the history of it itself will point to the history of repo-story and landry-ui which will complete the journey story of all of it and put a bow on it." Two books became three, recorded as decision record nine. The one-line description under each book comes from the July twenty-first trilogy-built session, prompt twenty-eight: "let's also add a brief, one short sentence that describes each book on the index page." The exact title wording — "a trilogy about its own making" — has no dictating prompt; it follows from that trilogy framing, an inference.

Next, the player itself, which gets its own book, so one paragraph here. It gives you a library view, per-chapter navigation with resume, adjustable playback speed, a time-synced transcript with follow and reading modes, and text-size control. It is vanilla JavaScript, a global called RepoStoryPlayer, with no build step — the landry-ui audiobook component, vendored rather than rebuilt. That reuse was a live decision. The foundation session records the hesitation, prompt twenty-eight, verbatim: "i am still conflicted about creating from scratch a reduced functionality user interface as opposed to reusing the landry ui." Prompt thirty-five resolves it: "reuse the landry ui, supersede adr 0002 — the tool is the audio book generator and player." And prompt forty-three locks the framing the whole site exists to show: "the product is the player and generator," the demonstration being their composition.

Now the feature built for the reviewer's clock: the Full and Summary toggle. Each chapter ships two tracks — the full arc, running roughly fifteen to twenty minutes, and a summary running three to four. The toggle sits beside the transcript label and flips between them. It is the best-documented feature in the repo. Its origin, from the trilogy-built session, prompt eleven, verbatim: "I fear the reviewer won't spend the time on it due to the workload they have. I propose a new feature... add two buttons to the right of the TRANSCRIPT pane label: Full and Summary." The re-issue adds discipline — "Don't do anything yet except generate the summary and show it to me" — so the summary was reviewed as text before any audio or interface existed. Prompt fifteen approved it and set the build order: "add the summary text as the final step of generating a chapter." Two corrections followed, both verbatim: prompt sixteen moved the buttons "to appear after the word TRANSCRIPT," and prompt twenty-three caught a bug where the chapter pane "is still the running length of the full length chapter" while summary was selected. The recap records the fix threading a computed summary clock through the whole time model.

Underneath the transcript is one durability detail. The read-along data lives in transcripts dot j-s-o-n, about five hundred thirty-six kilobytes of merged timing text. The page requests it with a cache key that reads v equals a-six-four-a-a-five-five-nine — the first eight characters of the file's own content hash, verified to match the bytes. Change the content, the key changes; leave it, the browser keeps its copy. No prompt asks for this; it is the repo's "durable over accurate" rule — key on content, not on modification time — an inference.

One feature is present but inert, and honesty requires saying so plainly. The site ships feedback dot j-s: a flag-a-transcription-error control, styled, with the logic to POST flags to a server. But the published page never passes it a feedback URL, and the site has no backend, so a flagged line is saved to local storage and goes no further. This is partial by design — the backend was retired in decision eight — and the feature degrades quietly rather than breaking. It is vendored code with no next-chapter prompt behind it.

The site is also installable and works offline, through a service worker in the file s-w dot j-s and a web manifest. It precaches the shell, caches each chapter's audio on first play, and slices cached files into partial byte-range responses so you can seek while offline. Its cleanup list evicts two stale entries: a legacy single-file book, and one recalled bad-generation chapter — chapter one-zero-seven-three — whose bytes had to be replaced under the same name. This machinery is vendored from the player, with no next-chapter prompt behind it, an inference — though an earlier war-game of the build plan is what forced the same-origin design that makes it work here at all.

A small thing you see in the browser tab: the favicon, in the file favicon dot p-n-g, is the Next Chapter program mark. Prompt thirty-one from the trilogy-built session reported the bug — "one small bug, no favicon" — and prompt thirty-two corrected the choice: "no, use the favicon from their site, not my old wbt icon," pointing at nextchapterproject dot org. It is wired through a registry key so the assembler copies it into place.

Last, the trail that lets a reviewer check all of this: the files provenance dot m-d and sources dot m-d. The first, auto-generated, pins the player to an exact landry-ui commit. The second, hand-written, pins each book's source — and records that this third book is narrated only through commit eight-two-nine-five-c-a-e, because, per decision record nine, a book cannot contain its own generation. That breadcrumb layer answers a foundation-session prompt, twenty-seven: "what mechanism does this repo provide so that the reviewer has an unambiguous breadcrumb trail to follow."

None of the files in the docs folder are hand-written. A script assembles every one of them. That is the next chapter.
