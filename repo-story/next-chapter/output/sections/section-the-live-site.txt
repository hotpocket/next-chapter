This is next-chapter, the public assembly repository, and the site you are listening on right now is the feature set: a library of three audiobooks about their own making, served as static files with no backend. This chapter tours the site; later chapters cover its assembly, its prompt trail, and the machinery underneath.

Start at the landing page, index dot h-t-m-l. Its browser title reads "Next Chapter — a trilogy about its own making." The markup is nearly empty; a single inline call hands the player the whole library as data — three books: repo-story, landry-ui, and next-chapter itself. Every book credits the same artist, Brandon Landry. Every chapter title carries a "Chapter N" prefix. Four chapters per book, each with a matching summary track.

That three-book shape is the product of two scoping prompts. The kernel is verbatim from the July twentieth foundation session, prompt twenty-eight: "the purpose of this project is to create the github page that is the interface to the audio books that talks about the repositories." It named landry-ui and repo-story, and fixed the site as a library of self-narrating books. The third arrived the next day, prompt twenty-one of the July twenty-first vendored session: "I want to add one more repo, this one: next-chapter... which will complete the journey story of all of it." Two books became three. The one-sentence description under each book answers a later trilogy-built prompt asking to "add a brief one short sentence that describes each book." The title phrase itself has no dictating prompt; it follows from that trilogy framing — an inference.

Next, the player — one paragraph, because it has its own book. It gives library view, chapter navigation with resume, playback speed, a time-synced transcript with follow and reading modes, and text-size control. It is vanilla JavaScript, one global named RepoStoryPlayer, no build step: the landry-ui audiobook component, vendored rather than rebuilt. The foundation session records the hesitation in prompt twenty-eight — "i am still conflicted about creating from scratch a reduced functionality user interface as opposed to reusing the landry ui" — and the resolution in prompt thirty-five: "reuse the landry ui, supersede adr 0002." Prompt forty-three locked the framing: the product is the player and the generator; the demonstration is their composition.

Now the feature built for the reviewer's clock: the Full and Summary toggle. Every chapter ships two tracks — the full narration, around seven minutes, and a summary, under two — with two buttons beside the transcript label to flip between them — the best-documented feature in the repository. Its origin is verbatim, trilogy-built session, prompt eleven: "I fear the reviewer won't spend the time on it due to the workload they have... add two buttons to the right of the TRANSCRIPT pane label: Full and Summary." The re-issued prompt added a text-first discipline — "Don't do anything yet except generate the summary and show it to me" — so the summary was reviewed as text before any interface or audio existed. Prompt fifteen approved it and set the build order: "add the summary text as the final step of generating a chapter." Two corrections followed. Prompt sixteen moved the buttons "to appear after the word TRANSCRIPT." Prompt twenty-three caught the chapter pane still showing "the running length of the full length chapter" in summary mode; the fix threaded a computed summary clock through the whole time model.

Underneath, one durability detail. The read-along text lives in transcripts dot j-s-o-n, the merged timing data for every chapter. The page requests it with a version key: the first eight characters of the file's own content hash. If the content changes, the key changes; if not, the browser keeps its copy. No prompt asks for this; it is the repo's standing durable-over-accurate rule — key on content, never on modification time — labeled inference.

One feature is present but inert: feedback dot j-s ships a styled control for flagging a transcription error, with logic to POST flags to a server. The published page never passes it a feedback URL, and there is no backend, so a flagged line is written to local storage and goes no further. Partial by design: the backend was retired in decision record eight; the feature degrades quietly. Vendored code, no next-chapter prompt behind it.

The site also installs and works offline, through a web manifest and a service worker in s-w dot j-s. The worker precaches the shell files, caches each chapter's audio the first time it plays, and slices cached files into partial byte-range responses so seeking works offline. Its cleanup list evicts two stale entries: a legacy single-file book, and one recalled bad-generation chapter, chapter one-zero-seven-three, replaced under the same name. All of it is vendored, no next-chapter prompt behind it — inference — though an earlier war-game of the build plan attacked the worker's same-origin assumption, forcing the in-repo hosting that makes this caching viable at all.

The newest feature is the quietest: the page counts its visitors. The July thirtieth session opens by asking, quote, "is there a way to install google analytics here or something like that so I know who hits this page and when?" The answer was not Google. The page carries a snippet for GoatCounter, a privacy-preserving hit counter: no cookies, no consent banner needed, recording only path, referrer, and a coarse browser and country — and its dashboard is public, open to anyone. The assembler emits the snippet from an optional analytics key in trilogy dot j-s-o-n, so the site code has one source of truth and a build without that key ships no third-party script at all. The same assembler prepends a cross-origin passthrough to the copied service worker, because the worker caches every response keyed by URL with no origin check, and the beacon's per-hit cache-buster would otherwise pile up quota-padded opaque cache entries. The README discloses all of it, answering the follow-up prompt: "is there a note in the readme that mentions and links to this?"

In the browser tab, the favicon, favicon dot p-n-g, is the Next Chapter program mark. Prompt thirty-one from the trilogy-built session reported it — "one small bug, no favicon" — and prompt thirty-two corrected the first fix: "use the favicon from their site, not my old wbt icon," pointing at nextchapterproject dot org. A registry key tells the assembler to copy it into place.

Last, the trail a reviewer can audit: provenance dot m-d and sources dot m-d. The first is auto-generated and records where the player was copied from, pinning a commit only when it can stand behind one. The second is hand-written and pins each book's source — including the rule that this third book is narrated only through a pinned commit, because, per decision record nine, a book cannot contain its own generation. The exact hash is an artifact of when the build ran; the pinned-range principle is verbatim. The whole layer answers foundation prompt twenty-seven, which asked what mechanism gives the reviewer "an unambiguous breadcrumb trail to follow."

None of the docs folder is written by hand. A script assembles every file. That script is the next chapter.
