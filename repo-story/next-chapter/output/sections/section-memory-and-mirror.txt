This last chapter covers the parts of the repository that exist so its claims can be checked: the configuration the sessions ran under, and the memory that carried context between them, both made readable to a reviewer who was never at the keyboard.

Start with the configuration. Throughout the project the agent ran under machine-level config that lives outside the repo, on the owner's laptop: global conduct rules, session hooks, a handful of skills. Vault notes and prompt exports refer to those files constantly, and a reviewer reading a clone cannot see any of them. The fix is a directory named dot-claude at the repo root holding actual copies. The whole feature comes from one prompt in the config-mirror session on July twentieth. The owner noticed that paths and skill references pointed at his local filesystem and wrote, verbatim, that this hides things from the reviewer. He asked for a local dot-claude folder whose contents mirror and duplicate the system files, but explicitly, so that a reviewer can see what I am running and can cross-reference paths they see in vault notes and other committed documents. He closed with an instruction to do a complete repo scan, update docs as needed, and commit. Every design property of the feature follows from that wording, and the decision is recorded as architecture decision record seven.

Because the prompt asked for a copy a reviewer can trust, the mirror is generated, never hand-typed. The generator is scripts slash sync-claude-mirror. It treats the global configuration as the single source of truth and derives the mirror from it: the orientation hook claude-orient and the push guard deny-git-push dot s h from the machine's bin directory, the global conduct file and settings, and four skills copied in full, conduct, vault, vet, and wargame. The browser skill, gstack, is about one point seven gigabytes upstream, so only its entry points come through, on an allowlist. The copy is rsync in archive mode, which preserves executable bits, with copy-links to resolve the skill symlinks that point into a dotfiles repo, and delete to prune anything stale. All of the script's roots, where the global config sits, where bin sits, where the mirror goes, are environment variables with computed defaults, never hardcoded absolute paths; that is the repo's durable-over-accurate rule applied to its own tooling. If any expected source is missing, the script exits with an error instead of writing a thin mirror, because a silently incomplete copy would misrepresent the setup. And a check mode dry-runs the sync and reports drift without writing anything; the project runs it as a gate before committing any change that touches configuration. None of those durability properties appear in the prompt. They are the standing rule, an inference about how trustworthy gets implemented, not a quoted instruction.

Not everything in the folder is inert. A companion README draws the line. The in-tree settings file and the in-tree skills genuinely load here, and the push guard runs from the copy inside dot-claude, so the rule that the agent never pushes is enforced by readable code that travels with every clone. The files suffixed dot-global are documentation only, deliberately unregistered, because the machine's global hooks already fire; loading the copies too would double-fire them, orientation twice per session, the brevity rule twice per prompt.

The mirror script has tests, and no prompt asked for them; they exist because of the project's standing rule, tests first, code second. The suite, test-sync-claude-mirror dot s h, builds a fake global, bin, and skills tree in a temporary directory through those same environment overrides, so it never touches the real machine config or the repo's own mirror. It runs six phases. Two of its teeth: one edits a source file and confirms check mode flags the drift, then that a resync clears it; another deletes a source file and confirms the sync fails loudly rather than producing a thin copy. The others verify that executable bits survive, symlinks resolve, stale mirror files get pruned, and the hand-written README and settings are left alone.

Next, memory. At the start of every session a hook, session-start dot s h, prints exactly three pointer lines into the agent's context: the latest recap, the count of open todos, the count of open probes. Pointers, never bodies; enough to orient, then read deeper on demand. It anchors itself to this repo's vault explicitly and delegates every read to scripts slash vault-digest, a plain grep-and-awk reader with subcommands for summaries, notes by type or by concern, the latest recap, todos, probes, backlinks, and full-text search. A design note dated June twenty-ninth, before this project began, records why it is built that way: dropping the Obsidian-app dependency made memory work headless and across parallel sessions. The repo inherits that machinery rather than authoring it; the foundation session's conduct-init command stamped the local copies in one stroke, and the mirror is what lets a reviewer read the actual scripts.

The memory itself lives in the vault directory, a real in-tree folder of Obsidian-compatible markdown. It holds the session records as recap-and-prompts pairs, each recap beside the exported prompts that drove it, plus todos, project notes, a vet, and the architecture decision records with an index. The instruction to keep those records is verbatim from the foundation session on July twentieth: let's start collecting A-D-Rs. Some are superseded, an S3 audio plan, an early plan to build a minimal player from scratch, and they are kept on purpose; others were never replaced at all, a Lambda ingestion path deferred to a later version, the two-books plan extended into the trilogy. The owner audited exactly that choice in the vendored session on July twenty-first, granting that in normal development superseded records are not removed, but asking for an audit for the sake of making the repo uncluttered, because the reviewer will not look at things that are hard to find or hidden behind clutter. The resolution keeps the superseded records under clear supersession banners with an index marking active versus retired, because the audiobooks narrate how the decisions evolved. And the policy stayed live to the day this chapter was recorded: on July thirtieth the pipeline narrating this book rewrote its own model split, the decision Fable plans, Opus executes giving way to Fable writes, Opus researches, because a newer model generation made Opus the stronger reasoner and Fable the stronger writer of English, while the enforcement, model pins in settings and in each agent's frontmatter, never moved. A model-to-task mapping is a dated decision, not a permanent one.

That closes the book. The published site, the assembler that builds it, the prompt trail behind every feature, and this mirror of the configuration it all ran under: the whole build is auditable end to end, which was the point from the first prompt to the last.
