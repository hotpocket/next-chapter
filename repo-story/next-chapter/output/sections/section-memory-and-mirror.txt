This final chapter is about the parts of the repository that let you check its own claims: the configuration the sessions ran under, and the memory that carried context between them, both made readable to someone who was never at the keyboard.

Start with the mirror. Throughout this project the agent ran under machine-level configuration that lives outside the repo, on the owner's laptop: global conduct rules, session hooks, a handful of skills. Vault notes and prompt exports refer to those files constantly, and a reviewer reading a clone can't see them. The fix is a directory named dot-claude at the repo root that holds actual copies of that configuration. The whole feature traces to one prompt from the config-mirror session on July twentieth. The owner noticed that paths and skill references in the repo pointed at the local filesystem and, in his words, this hides things from the reviewer. He asked for a local dot-claude folder where those things are kept, files that mirror and duplicate the system files but are done so explicitly, so that a reviewer can cross-reference paths they see in vault notes and other committed documents. He closed with: do a complete repo scan and update docs as needed, then commit. Every property of the feature follows from that wording, and the decision is recorded as architecture decision record seven.

Because the prompt asked for an explicit copy a reviewer can trust, the mirror is generated, never hand-typed. The script that generates it is scripts slash sync-claude-mirror. It treats the global configuration as the single source of truth and derives the mirror from it. It pulls the orientation hook claude-orient and the live push-guard deny-git-push dot s h from the machine's bin directory; the global conduct file and settings; and four skills in full, conduct, vault, vet, and wargame. The browser skill, gstack, is roughly one and a half gigabytes upstream, so only its entry points are copied through an allowlist. The copy itself is rsync with archive mode to preserve executable bits, copy-links to resolve the skill symlinks that point off into a dotfiles repo, and delete to prune anything stale. The script's roots, where the global config is, where bin is, where the mirror goes, are all read from environment variables with computed defaults, so nothing is a hardcoded absolute path; this is the repo's durable-over-accurate rule applied to its own tooling. If any expected source is missing, the script exits with an error rather than writing a thin mirror, because a silently incomplete copy would misrepresent the setup. And a check mode does a dry run and reports drift without writing, which is the gate the project runs before committing anything that touches configuration. The durability details aren't spelled out in the prompt; they're the standing rule for how trustworthy gets implemented, an inference rather than a quoted instruction.

Not everything in that folder is live. A companion README draws the line. The in-tree settings and the in-tree skills actually load here, and the push guard genuinely runs from the copy inside dot-claude, so the rule that the agent never pushes is enforced by readable code that travels with the clone. The files suffixed dot-global are documentation only, deliberately not registered, because the machine's global hooks already fire; loading the copies too would double-fire them, orientation twice per session, the brevity rule twice per prompt.

The mirror script has tests, and no separate prompt asked for them. They exist because of the standing rule on this project: tests first, code second. The suite, test-sync-claude-mirror dot s h, builds a fake global, bin, and skills tree in a temporary directory through those same environment overrides, so it never touches the real machine config or the repo's own mirror. It runs six phases. Two of its teeth: one phase edits a mirrored file and confirms check mode flags the drift, then that a resync clears it; another removes a source file and confirms the sync fails loudly instead of producing a thin copy. It also verifies exec bits survive, symlinks resolve, stale files get pruned, and the hand-written README and settings are left untouched.

Next, memory. At the start of every session a hook, session-start dot s h, prints exactly three pointer lines into the agent's context: the latest recap, the count of open todos, the count of open probes. Pointers, never bodies, enough to orient, then read deeper on demand. It anchors explicitly to this repo's vault and delegates every read to scripts slash vault-digest, a plain grep-and-awk reader with subcommands for summaries, notes by type or concern, the latest recap, todos, probes, backlinks, and full-text search. A design note dated June twenty-ninth, before this project began, records the reason it's built that way: dropping the Obsidian-app dependency lets memory work headless and across parallel sessions. This project inherits that machinery; the foundation session's conduct-init command stamped the repo-local copies in one stroke, and the mirror is what surfaces the scripts so a reviewer can read them.

That memory lives in the vault directory, a real in-tree folder of Obsidian-flavored markdown. It holds the session records, four recap-and-prompts pairs, each session's recap beside the exported prompts that drove it, plus todos, project notes, a vet, and nine architecture decision records with an index. The instruction to keep them came from the foundation session on July twentieth: let's start collecting A-D-Rs. Some of those records are superseded, an S3 audio plan, a Lambda ingestion path, an early two-books plan, and they are kept on purpose. The owner audited exactly that choice in the vendored session on July twenty-first, noting that normally superseded records are kept and not removed, but asking for an audit of the repo for the sake of making it uncluttered, since the reviewer won't look at things that are hard to find or hidden behind lots of clutter. The resolution: keep the superseded records with clear supersession banners and an index marking active versus retired, because the audiobooks narrate how the decisions evolved. Much of this vault convention predates the project; it's the standing setup the conduct scaffold installs, not something authored line by line here.

And that closes the book. The published site, the assembler that builds it, the prompt trail behind every feature, and this mirror of the configuration it all ran under: the whole build can be audited end to end, which was the point from the first prompt to the last.
