Chapter two. The player from chapter one plays whatever a registry hands it; this chapter is how the published site, the docs directory, gets built from three separate pipeline runs.

Start with the registry: scripts slash trilogy dot json. A small configuration file, and the whole plan for the site in data form. It carries a title — "Next Chapter, a trilogy about its own making" — a favicon key, and three books, each naming a slug, manifest path, transcripts path, and one-line description. Those paths point into per-book run folders under repo-story, where the audio is gitignored but narration text and transcripts stay tracked and diffable. No prompt dictates this file; it is where decisions made elsewhere — which three books, the site's title, the favicon — get recorded as config for the assembler to read.

Next, the assembler: scripts slash build dash trilogy dash site. It reads the registry and, for each book, converts the chapters manifest into the player's book structure with a function named book from manifest — and here is the design choice worth naming. It does not reimplement that conversion; it imports the function from build underscore site dot py in the repo-story tree, the same code the pipeline itself uses to build a single book. One source of truth, derived from rather than copied, so the two can never drift. That is the standing "durable over accurate" rule applied: no prompt says reuse this function, the rule says it.

It then copies each book's audio into docs slash audio slash the slug: every chapter file and any summary file — but only when the destination is missing or a different size on disk, so rebuilds skip unchanged audio. Then it prunes: any file in the destination the new manifest does not expect gets reported as removing stale, and unlinked. Only after the copy — which needs the plain names to find its source files — does it prefix every filename with the slug, so a book's first chapter becomes its slug, then slash, then chapter underscore zero zero zero one, keeping three books from colliding in one flat player.

The transcripts from all three books merge into a single transcripts dot json, and its cache-busting URL comes from the content itself: a sha256 hash of the merged bytes, first eight hex characters, as a version query string. Change the content, the key changes; unchanged content keeps the browser's cache. A content hash, not a timestamp. Then it copies the player's own files — player dot js, player dot css, the service worker, and the rest — plus the icons folder if present, and generates index dot html with all three books inlined into the player's init call. This generator writes no feedback URL — which is why, as chapter one noted, the live feedback panel is inert.

Two additions from July thirtieth: first, the registry gains an optional analytics key. When it names a site code for goatcounter, a privacy-preserving hit counter, the assembler derives the endpoint and emits one script tag into the page head; when the key is absent, the page carries no third-party script at all — the site code lives in the registry, nowhere else. The second addition guards the service worker. The player's worker caches every response it fetches, keyed by URL, with no origin check, and the analytics beacon carries a per-hit cache-buster — every pageview would mint a new opaque cache entry, which browsers pad to a fixed multi-megabyte size against the origin's storage quota — unbounded growth crowding out the cached audio. So the assembler patches the copied service worker on its way into docs, prepending a passthrough that catches cross-origin requests before the caching handler sees them. Prepending rather than editing the upstream handler survives player-component drift; a marker makes the patch idempotent, so rebuilds never stack the guard. The tests assert the derived endpoint, the guard applied exactly once, and an opted-out build with no analytics.

Now the provenance rule, the sharp one. The player component is a copy of an external UI project, landry dash u i. When the assembler records where the player came from, it shells out to git, reads the origin remote and the repository's top-level name, and pins an exact commit only if landry dash u i actually appears there — a genuine checkout of that project. Otherwise it writes a plain, unpinned description. The in-code comment gives the reason: pinning that repository's HEAD would be, quote, provenance theater — a hash pointing at whatever repo encloses the directory is worse than no hash. The result goes into docs slash PROVENANCE dot md, two honest lines: where the player was copied from, and that the audio and transcripts come from the run folders named in the registry. The recap for the twenty-first records that this fix came from a research and QA pass, not a prompt — the assembler had been pinning the enclosing repo's HEAD.

That fix is frozen into the tests. The assembler ships with test underscore build underscore trilogy underscore site dot py, which exists because of one instruction from the twenty-first, the trilogy-built session, issued before any build code: "you see your directives to test first write code second right?" The test builds two fake books in a temporary directory, plants a fake player inside an unrelated git repository, and asserts the whole contract — filenames slug-prefixed, a summary file passing through, the registry's favicon replacing the player's default icon. And the load-bearing negative one: the provenance string must contain no " at " marker — no pinned hash — precisely because the fake player sits in an unrelated repo, encoding the provenance-theater fix as a regression test. The test runs on the standard library alone.

One more piece, covered in full by book two but named here: the vendored generator. The repo-story tree inside this project, and its build script scripts slash vendor dash repo dash story, exist because of a decision from the twenty-first vendored session. The prompt: "let's create this repo as a folder within next-chapter... let's replay the commits excluding all personal info and unnecessary info you found." Rather than flip a private repository public, the owner had it replayed commit by commit into this repo, each snapshot scrubbed of excluded files and private text, each carrying a Replayed-From trailer back to its original. The script refuses to run on main, and ships a verify mode that scans every replayed commit for banned tokens. That is the vendoring decision; book three tells how a leak was caught mid-flight.

And nothing here deploys — the assembler assembles docs and stops. Publishing is the owner's git push, a policy a PreToolUse hook enforces mechanically by blocking any agent push. The prompt from the twenty-first says it directly: do a final check for personal info, then, quote, give me the command to flip it public (the gh command), and i'll push it after that. The assembler and registry themselves have no single authorizing prompt; they trace to an approved plan milestone and dated commits — that is inference, labeled as such.
