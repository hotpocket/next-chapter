Chapter two. The player from chapter one plays whatever a registry hands it. This chapter is how the published site, the docs directory, gets built from three separate pipeline runs into one thing the player can load.

Start with the registry itself: scripts slash trilogy dot json. It is a small configuration file, and it is the whole plan for the site in data form. It carries a title — "Next Chapter, a trilogy about its own making" — a favicon key, and a list of three books. Each book entry names a slug, a manifest path, a transcripts path, and a one-line description. The manifest and transcript paths point into per-book pipeline run folders under repo-story, and those folders are gitignored: the inputs are generated outputs, not committed files. No prompt dictates this file line by line. It is the place where decisions made elsewhere — which three books, what the site is called, which favicon — get written down as config for the assembler to read.

Next, the assembler: scripts slash build dash trilogy dash site. It reads the registry and, for each of the three books, runs the same sequence. It converts that book's chapters manifest into the player's book structure by calling a function named book from manifest — and here is the design choice worth naming. It does not reimplement that conversion. It imports book from manifest from build underscore site dot py inside the repo-story tree, the same function the pipeline itself uses to build a single book. One source of truth, derived from rather than copied, so the two can never drift apart. That reuse is the project's standing "durable over accurate" rule applied: no prompt says reuse this function, the rule says it.

Having built each book, the assembler copies that book's audio into docs slash audio slash the slug. It copies each chapter file and, when a chapter has one, its summary file — but only when the destination is missing or a different size on disk. A size-compare skip, so re-running the build does not recopy unchanged audio. Then it prunes: any file already in the destination that the new manifest does not expect gets reported as removing stale, and unlinked. Only after the copy does it prefix every filename with the slug, so a book's first chapter becomes, for example, its slug then slash then chapter underscore zero zero zero one, keeping the three books from colliding in one flat player. The order matters — the copy uses the plain names to find the source files, and prefixing happens after.

The transcripts from all three books get merged into a single transcripts dot json, and the assembler builds the player's cache-busting URL from the content itself: it takes a sha256 hash of the merged bytes and uses the first eight hex characters as a version query string. Change the transcript content, the key changes; leave it unchanged, the key holds, and the browser keeps its cache. A content hash, not a timestamp. Then it copies the player's own files — player dot js, player dot css, the service worker, and the rest — from the player source directory, copies the icons folder if present, and generates index dot html with all three books inlined directly into the player's init call. Notably this generator writes no feedback URL, which is why, as chapter one noted, the feedback panel on the live site is inert.

Now the provenance rule, and this is the sharp one. The player component is a copy of an external UI project, landry dash u i. When the assembler records where the player came from, it will pin an exact commit only when the player directory is genuinely a checkout of that project — it shells out to git, reads the origin remote and the repository's top-level name, and pins the commit hash only if landry dash u i actually appears there. Otherwise it writes a plain, unpinned description instead. The in-code comment gives the reason: pinning that repository's HEAD would be, quote, provenance theater. A hash that looks like provenance but points at whatever repo happens to enclose the directory is worse than no hash. It writes the result into docs slash PROVENANCE dot md, two honest lines: where the player was copied from, and that the audio and transcripts come from the pipeline run folders named in the registry. The recap for the twenty-first records that this fix came out of a research and QA pass — the assembler had been pinning the enclosing repo's HEAD when the player directory was not a real checkout — not from a prompt.

That fix is frozen into the tests. The assembler ships with test underscore build underscore trilogy underscore site dot py, and it exists because of one instruction. From the twenty-first, the trilogy-built session, before any build code was written, the prompt read: "you see your directives to test first write code second right?" The test builds two fake books in a temporary directory, with a fake player placed inside an unrelated git repository, and asserts the whole contract in fourteen checks — that filenames come out slug-prefixed, that a summary file passes through, that the registry's favicon replaces the player's default icon. And the load-bearing negative one: it asserts that the provenance string contains no " at " marker — no pinned hash — precisely because the fake player sits in an unrelated repo. That single assertion encodes the provenance-theater fix as a regression test. The test runs on the standard library alone, no audio tooling required.

One more piece, covered in full by book two but named here: the vendored generator. The entire repo-story tree inside this project, and its build script scripts slash vendor dash repo dash story, exist because of a decision from the twenty-first vendored session. The prompt: "let's create this repo as a folder within next-chapter... let's replay the commits excluding all personal info and unnecessary info you found." Rather than flip a private repository public, the owner had it replayed commit by commit into this repo, each snapshot scrubbed of excluded files and private text, each carrying a Replayed-From trailer back to its original. The script refuses to run on main, and ships a verify mode that scans every replayed commit for banned tokens. That is the vendoring decision; book three tells how a leak was caught mid-flight.

And nothing here deploys. The assembler assembles docs and stops. Publishing is the owner's git push — the policy a PreToolUse hook enforces mechanically by blocking any agent push. The prompt from the twenty-first states it directly: do a final check for personal info on all files, then, quote, give me the command to flip it public, and i'll push it after that. The assembler and the registry themselves have no single authorizing prompt; their existence traces to an approved plan milestone and dated commits, and I am labeling that as inference.
