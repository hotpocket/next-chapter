Chapter four. Adopting the player, and the tests that keep it honest.

The player you have been hearing about is a component, and a component has to be fetched into whatever project wants to use it. That job belongs to a shell script named luinst. You run it with two arguments: the path of the component you want, and the destination directory to drop it into. Under the hood it makes a temporary directory, does a shallow one-commit clone of the landry-ui repository into it, and confirms the requested component path actually exists in the clone. Then it does the blunt thing its callers depend on: it removes the destination directory entirely, recreates it, and copies the component's contents in. A fetch is a replacement, not a merge, so the fetched copy is always exactly what the repository holds, with nothing stale left behind. The typical call pulls the vanilla player into a project's player directory, and the consuming project gitignores whatever luinst drops there, because the fetch is the source of truth.

Which repository, and cloned how? By default luinst clones over HTTPS from the public landry-ui repository, and that default is recent. It exists because of the July twentieth session, where the whole repository was flipped from private to public. The prompt that opened that work read: "this repo will serve the site. do an audit on landry-ui to see if it is safe to flip public. wargame that audit to have as much confidence in the analysis as possible." Once the audit passed, the next instruction was two words: "run the gh flip command yourself." A public repository means consumers no longer need SSH authentication to clone it, so the default clone URL became HTTPS. A follow-up prompt from the same session handled the paperwork: "use my voice, that is fine. fix luinst https path in docs. then drop them from the todo in the session recap." The SSH form is still there for anyone who wants it, reachable by setting the LANDRY underscore UI underscore REPO environment variable.

Next, the embed contract. Once luinst has dropped the vanilla player into a project, the host page wires it up with three tags and one call: a stylesheet link to player dot css, a script tag for feedback dot js loaded before player dot js, and then a call to RepoStoryPlayer dot init with an options object. That object is the contract. It takes a container element, which is required; a books array; an audioBaseUrl that defaults to the string "audio slash"; a transcriptUrl; an optional feedbackUrl; and a title for the library heading. Point those at real data and the player runs.

There is a second variant of the player, written in TypeScript with Tailwind and marked use-client, exported as an AudiobookPlayer component. It is deliberately behind the vanilla one, and that is a recorded decision rather than a captured prompt. The session note from early April lists the reasoning in the user's own shorthand: vanilla JavaScript over React for the canonical player, more portable, no build step, with React described as feature-complete but not yet optimized like vanilla. Concretely, the React variant runs on the old single-file audio model, one audio element seeking by chapter start-second offsets, where vanilla loads a separate file per chapter. It has no Full-versus-Summary toggle, no reading mode, no text-size stepper, no offline download. It carries a couple of things vanilla lacks, like arrow-key seeking of ten seconds, but it is the older, un-migrated cousin, kept working and left behind on purpose.

One feature crosses that line in an interesting way: the flag button, the control a listener would tap to report a bad transcription. In the React variant it is fully rendered, a warning glyph that turns red when flagged and posts a small payload to the feedback endpoint. In the shipped vanilla player it is not. The wiring is all present: feedback dot js fully defines flag, unflag, and is-flagged, the init call starts the feedback module, and the chunk-flag styling sits in the stylesheet in red. The payload it would send names the project as repo-story, the type as transcription-error, and carries the book slug, chapter and chunk index, the chunk text, and a timestamp. But player dot js never renders the button and never calls those functions. Flagging is wired and styled and unreachable, and that too is deliberate. The April session note keeps it as a TODO: feedback flagging UI removed, re-add when the backend is deployed.

Two small tools round out the toolkit. There is serve dot py, a threaded development server whose whole reason to exist is that Python's stock file server does not honor Range requests, and audio seeking needs them. It parses a byte range, replies with a 206 partial-content status and the correct Content-Range header, and streams the file back in sixty-four-kilobyte chunks. And there is check-m4b, a Python validator with no file extension, a fossil of an older architecture. It confirms that an M4B's moov atom sits at the front for fast starting, printing the exact ffmpeg fix command if it does not, then checks that the codec is AAC, that chapters are present, and that the duration is positive. The shipped player consumes per-chapter M4A files, not one big M4B, so check-m4b validates a build path the player no longer takes. It is kept, but it is legacy.

Finally, the part that earns trust: the tests. There are two suites, both Node ES-module scripts driving Playwright, the headless browser-automation library, resolved from a local pinned copy. One is follow dot test dot m-j-s, contracts A through M, written across the un-exported July sixteenth push alongside the follow-scroll and reading-mode work, so its provenance is the commits, not a captured prompt. The other is summary dot test dot m-j-s, contracts A through G, and it has a verbatim anchor. The July twenty-first session that built the Full-versus-Summary toggle opened with the user invoking the house rule. The prompt read: "you see your directives to test first write code second right?" That is why the summary contracts exist as a suite rather than an afterthought. Those contracts check real behavior: that toggling to Summary loads the summary M-four-A and shows chunks starting with the words "Summary one"; that total time reads twelve seconds; that clicking the third summary chunk moves the clock to about three seconds; that summary mode survives a page reload; and that a book with no summaries hides the toggle entirely. Both suites run against a synthetic fixture built by gen dot s-h, which uses ffmpeg to generate two silent audio chapters and a fake transcript, including one book with summaries and one without, precisely to exercise that last branch.

And that closes the book. This player, the vanilla one, fetched by luinst into the trilogy site, is the one speaking this sentence to you right now.
