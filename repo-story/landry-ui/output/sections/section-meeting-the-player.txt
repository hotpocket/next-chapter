Meeting the player.

The thing playing this narration to you right now is itself the subject of this book. It is landry-ui, a component library written in plain, build-free JavaScript, and its audiobook player is the component we are walking through. Four chapters: this one is the player's core — how it lists books, models sound, and moves through a recording. The second is the reading surface, the words on screen. The third is going offline. The fourth is how it plugs into the rest of the system, and the tests that hold it in place.

One honesty note first, said once. Almost everything in this chapter was built early, between April and May, well before this project began exporting the prompts that drove it. So for these features no word-for-word prompt survives. What survives is the commit message and a session note from early April, both of which paraphrase the work rather than quote the instruction. Where even a commit is silent, it is called inference. I will not dress any of these up as the user's exact words.

Start with what you see first: the library view, drawn by a routine named renderLibrary. It lists each book with a single meta line — the chapter count, a middle dot, the total duration — and a small colored progress dot beside it. That dot is gray when untouched, blue when a book is in progress, green once it is past ninety-eight percent complete. The heading is configurable: the calling page can pass a title, and if it passes none, the word "audiobook" stands in. That fallback, and a fix so that automatically resuming your last book no longer overrides the library screen, both landed together in a commit on the second of April; the commit message is the only record of the request.

Underneath the library sits the resume system. As you listen, the player writes your position to your browser's local storage every five seconds, and again when you leave the page, and again each time a chapter ends. It writes two things: a per-book progress record, keyed by the book's index, holding your book-time and how far through you are; and a pointer to the last book you had open. Reopening the page with no other instruction auto-resumes that last book. There is a subtle rule here, recorded in the session note as a mistake to avoid: when you return to the library, the code must actively forget the last-book pointer, or the five-second save would quietly set it again and pull you back into the book.

Now the heart of it — how the player models sound. A book is not one giant audio file. It is a set of per-chapter files, one small M4A per chapter, and only one is loaded into the single audio element at a time. This is the pivotal architecture decision of the whole component, made in a commit on the twenty-sixth of April. Why a single file was abandoned is not preserved in any prompt; a later session recap, looking back, remembers the old model as one file that had swelled to gigabytes — impractical to load and seek — so the player switched to per-chapter files. Because only one chapter is in memory, the audio element's own clock runs chapter-local, and the player computes a book-wide time on top of it: the chapter's start offset plus the local time. Finding which chapter a given book-time belongs to is a binary search across the chapter starts. That recap is a downstream witness describing the consequence; the instruction that caused the change is inference.

That data model surfaces as the chapter panel down one side of the player. Each chapter is a row with its title, its duration, a progress fill that tracks only while that chapter is the active one, and a small scrubber handle. The panel is responsive in an unusual way: it declares itself a container, and when it is squeezed below a hundred and fifty pixels wide, the titles and durations vanish and each row collapses to a short label — "Ch" and the number. That narrow-label behavior is described in the April session note as a container-query feature, again as a summary of the work, not a quote.

Next, the transport bar along the bottom. Minus thirty seconds, previous chapter, play and pause, next chapter, plus thirty seconds, and a speed button. Skipping preserves whether you were playing or paused. The speed button cycles a fixed list — zero-point-seven-five, one, one-and-a-quarter, one-and-a-half, one-and-three-quarters, and two — starting at normal speed and stepping through on each tap, wrapping around. Speed is deliberately not remembered between sessions.

Above those buttons is the track bar, and it is more careful than it looks. Dragging it uses pointer capture, so once you grab the thin bar your drag keeps working even as your finger or cursor strays off it. While you drag, the fill and the time readout follow you live, and if your target lands inside the chapter already loaded, the audio seeks in real time; only when you release into a different chapter does it load that chapter's file — because loading on every move would thrash the audio. Small ticks along the bar mark where each chapter begins. One honest detail: the drag math and those chapter ticks are computed against the full book clock, while the passive progress fill uses the summary-aware clock we will meet in chapter two. In ordinary playback the two agree; in summary mode they do not perfectly coincide. That is simply what the code does at this revision, narrated by no test. The two commits behind the bar, both on the sixteenth of July, name the behavior plainly — "drag-to-seek across chapters" and a "hover thumb riding the progress edge" — but they fall just before prompt exporting began, so the wording is the commit's, not the user's.

Last, the address bar itself is a control. Each book has a slug, and opening a book pushes a short hash route so the position is shareable; an empty hash means the library. Moving back and forward in the browser moves the player with it. That routing arrived whole in a single commit on the sixth of May, and only its subject line records the intent.

Sound is half the player. The words on screen are the other half.
