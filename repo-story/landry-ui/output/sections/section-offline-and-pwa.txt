Chapter three: taking the book offline.

One honesty note covers the whole chapter. Everything here was built in a concentrated burst in early April of twenty twenty-six, months before this project began exporting its prompts. No verbatim prompt survives for any feature you are about to hear. What survives is unusually good for a non-prompt source: a detailed session note dated the third of April that records the lessons, and a commit trail dense enough to narrate itself. Every attribution in this chapter is a paraphrase of those commits and that note, never a quote of the developer's words.

First, what the listener sees: the download button. Each book in the library carries a control that pulls the whole thing down for offline listening. Press it and the button flips to a preparing state, its text reading "Preparing," its tooltip warning you to keep the page open. Behind it, a function named downloadForOffline takes a screen wake lock if the browser offers one, so the device cannot sleep mid-transfer, and installs an unload guard, so an accidental refresh asks for confirmation instead of silently killing the download. Then it fetches the app shell, the page and styles and scripts and manifest and icons, and after that the chapters, one at a time, in order. Each real fetch updates the button with a running count, the current chapter number over the book's total. For every chapter it stores both the full track and, where one exists, the summary track; the code's own comment gives the reason: offline must work in either listening mode. On success the button settles into a downloaded state with a check mark. On failure it offers a retry.

The structural fact underneath is per-chapter caching. Everything the download fetches lands in a single audio cache, one entry per file, keyed by the file's absolute URL. Adding a new chapter to a deployed book never invalidates the chapters already saved; the download skips anything already cached, silently, with no flash in the UI, and fetches only what is missing. A companion check runs when the library renders: it probes the cache for each book's first and last chapters, and if both are present it shows the button as already downloaded. The code's comment calls this a heuristic, a fast approximation rather than proof that every byte is on disk.

Next, the service worker, the file sw dot js, which makes offline work at fetch time. It keeps two caches, and the split is deliberate. One is named audiobook dash shell and holds the application's files; the other is named audiobook dash audio and holds the chapters. The session note records the reasoning as an architecture decision: separate shell and audio caches, so code updates don't wipe audio. On install the worker precaches the shell, meaning the page itself, player dot css, player dot js, feedback dot js, transcripts dot json, the manifest, and both icons, and afterward serves it network-first: fresh when online, cached when not. The audio cache is the opposite, cache-first: once a chapter is stored, it plays from disk and never touches the network again. One footnote sits outside this repository, and it is current as of the thirtieth of July: the shell handler caches every response it fetches, keyed by URL, with no origin check, so the consuming site's assembler, a build script in the next-chapter repository rather than anything in landry-ui, prepends a cross-origin passthrough to its copy of sw dot js. Without it, a third-party analytics beacon carrying a per-hit cache-buster would mint a fresh opaque cache entry on every pageview, and browsers pad opaque entries to a fixed multi-megabyte size against the origin's storage quota.

That cache-first audio path holds the chapter's central lesson, and it is about seeking. A cached chapter is stored whole, as one complete two hundred response, keyed by its URL with the Range header stripped. But audio elements ask for byte ranges, so dragging the scrubber requests a slice, not the file. A helper called serveRange answers those requests from the whole cached file: it reads the cached response as a Blob, parses the requested start and end bytes, and returns exactly that slice as a two oh six partial response with correct content-range headers. The lesson is in how it slices, and it is recorded three times over, in the commit, in the session note, and in the repository's own CLAUDE file under performance lessons. It uses Blob dot slice, never arrayBuffer. Reading the cached file as an array buffer pulls the entire file, seven hundred megabytes and more, into memory on every single seek; Blob dot slice returns a lightweight reference to just the requested bytes. The documented framing is blunt: the difference between twenty-second seeks and instant seeks. The note preserves a companion lesson from the same days: cache keys must be absolute URLs. A commit dated the fourth of April fixed the offline cache by storing and looking up every entry by full absolute URL.

The download code's shape also records two dead ends. A commit from the second of April adopted a background-fetch API for downloads, and a later commit the same day removed it entirely; the session note records it as unreliable, with partial downloads, no resume, and stale state, which is why the shipped download is a plain sequential fetch into the cache. The second dead end was memory. On tablets, early versions accumulated incoming bytes and ran out of memory around four point six gigabytes; cloning the response stream didn't help, because the browser buffers both copies. The note records the fix as a byte-counting stream wrapper handed straight to the cache, and the button was rewritten several times chasing that crash before it settled.

The worker also carries a recall mechanism. On activate it deletes any cache that isn't one of its two current names, and it evicts two named legacy keys from the audio cache. One is the single-file audiobook from the prior architecture. The other is a chapter recalled after a bad generation shipped, a leaked voice sample; a commit from the third of July twenty twenty-six evicts it so the fix reaches listeners' already-downloaded caches. That commit is the one moment in this chapter later than April, and its subject states the reason plainly.

Finally, install. The web manifest, manifest dot webmanifest, names the app "Audiobook Player," short name "Audiobook," with standalone display, so it opens without browser chrome. Background and theme colors are both near-black, and it declares two icons, at one ninety-two and five twelve pixels, both present on disk. Installability rests on the served page linking that manifest plus the registered worker; player dot js registers sw dot js on load wherever service workers are supported.
