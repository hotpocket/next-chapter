Chapter three: taking the book offline.

One honesty note up front, and it holds for the whole chapter. Everything here was built in a concentrated burst in early April of twenty twenty-six, months before this project began exporting its prompts. No verbatim prompt survives for any feature in this chapter. What survives instead is unusually rich for a non-prompt source: a detailed session note from the third of April that records the lessons, plus a dense, self-narrating trail of commits. So every attribution you hear is a paraphrase drawn from those commits and that note, never a quote of the developer's words. Where the note records a lesson, I will say the note records it.

Start with what the listener sees: the download button. In the library view, each book carries a control that pulls the whole thing down for offline listening. Press it and the button immediately switches to a preparing state, its text changing to "Preparing," its tooltip warning you to keep the page open. Behind that, a function called downloadForOffline goes to work. It requests a screen wake lock, if the browser supports one, so the device won't sleep mid-download, and it installs a guard against accidental navigation, so a stray tap on the back button prompts a confirmation instead of silently killing the transfer. Then it fetches the app shell — the page, the styles, the player script, the manifest, the icons — and after that the chapters, one at a time, in order. As each real fetch lands, the button counts your progress: "Chapter one of twelve," "chapter two of twelve," and on. For every chapter it stores both the full track and, where one exists, the summary track, because offline listening has to work in either mode. When it finishes, the button settles into a downloaded state with a check mark; if a fetch fails, it flips to a retry state instead.

The important structural detail is that everything downloaded goes into a single audio cache, keyed per file. Each chapter is its own cache entry, stored by its own absolute URL. Adding a new chapter to a book later never invalidates the ones already saved — the download simply skips anything already cached, silently, with no flash in the UI, and fetches only what's missing. There's also a lightweight status check that runs when the library renders: it probes the first and last chapter of each book, and if both are present it shows the book as already downloaded. The code's own comment is honest that this is a heuristic, a fast approximation, not a rigorous check that every byte of every chapter is on disk.

Next, the service worker — the file sw.js, the piece that makes offline actually work at fetch time. It keeps two caches, and the split is deliberate. One is named audiobook-shell, holding the application's own files; the other is named audiobook-audio, holding the chapters. The reason for two is recorded in the session note as an architecture decision: code updates rebuild the shell cache, but they must never wipe the audio you've already downloaded. So the shell is precached on install and served network-first — fresh when you're online, cached when you're not — while the audio cache is persistent and served cache-first. Once a chapter is saved, it plays from disk and never touches the network again.

That cache-first audio path is where the central lesson of the chapter lives, and it is about seeking. A cached chapter is stored as a single complete file, a normal two hundred response. But audio players don't ask for whole files; they ask for byte ranges, so dragging the scrubber jumps straight to a spot. The service worker has to answer those range requests out of a file it holds whole. A helper called serveRange does it: it reads the cached response as a Blob, parses the requested start and end bytes, slices out exactly those bytes, and returns them as a two-oh-six partial response with the correct content-range headers. The lesson — enshrined in the commit, in the session note, and in the player's own CLAUDE file under "performance lessons" — is how it slices. It uses Blob dot slice, never arrayBuffer. Reading the file as an array buffer would pull the entire chapter, seven hundred megabytes and up, into memory on every single seek. Blob dot slice returns a lightweight reference to just the requested bytes. The note frames it bluntly as the difference between twenty-second seeks and instant seeks. A companion lesson from the same session: cache keys must be absolute URLs. An earlier version keyed entries by relative path and the offline lookups missed; the fix, in a commit dated the fourth of April, was to store and look up every chapter by its full absolute URL.

The shape of the download code is also a record of two dead ends, and the note preserves both. The first was a background-fetch API. A commit adopted it for offline downloads and a later commit reverted it entirely; the note explains that it proved unreliable — partial downloads, no resume, stale state — so the shipped version is a plain sequential fetch straight into the cache. The second was memory. On tablets, the early download accumulated the incoming bytes and ran out of memory around four and a half gigabytes. Cloning the response stream didn't help, because the browser buffers both copies. The note records the fix as a byte-counting stream wrapper that hands bytes to the cache without holding the whole file, and the download button was rewritten several times chasing that crash before it settled.

One more piece of the audio cache is a recall mechanism. On activate, the worker deletes any cache that isn't one of its two current ones, and it also evicts two specifically named legacy keys. One is a leftover from the old single-file architecture. The other is a chapter that shipped with a bad generation — a leaked voice sample — and had to be purged from listeners' already-downloaded caches. That eviction, in a July commit, is the one moment in this chapter later than April, and its purpose is written plainly in the commit subject.

Finally, install. A web manifest, manifest.webmanifest, is what lets the player install as a standalone app. Its name is "Audiobook Player," its short name "Audiobook," its display mode standalone, so it opens without browser chrome. Its background and theme colors are both a near-black. It declares two icons, at one hundred ninety-two and five hundred twelve pixels, and both files exist on disk. Installability rests on the served page linking that manifest and registering the service worker, which player.js does on load.

That's the listener's side. Now the developer's: how this player ships into other projects, and how it's tested.
