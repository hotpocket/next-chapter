Last chapter ended with rendered audio on disk. This chapter turns that audio into a site you can open and play.

First, build_transcripts.py, the script behind the read-along you may be following right now. Its job is to line the words up with the sound. It imports the same chunking logic the audio builder uses, so a transcript chunk and its audio are always the same slice of text. For each chapter it re-splits the text into chunks, probes each chunk's WAV file for its duration, and records a start and an end, rounded to three decimals. Timestamps are chapter-relative: every chapter's first chunk starts at zero. If a chunk's WAV is missing, the script prints a warning and truncates that chapter rather than guessing. The output is one file, transcripts.json, holding books, chapters, and chunks — and, when a chapter has a summary text file, a second parallel timeline called summary_chunks with its own timestamps.

How it finds those WAV files matters, because this is where drift used to be possible. Chunk WAVs are content-addressed: each is named by a hash of its chunk's text together with the voice and the speech parameters it was rendered with. build_transcripts.py does not rebuild those names from a position number. It imports chunk_filename and chunk_key from build_audio.py — the same functions that named the files at render time — and reads the voice and parameters back from cache-params.json, a sidecar the render wrote beside the chunks. Writer and reader derive every filename from the same code and inputs, so they cannot disagree about what a chunk is called.

The base alignment feature has no verbatim prompt; it arrives in an April second commit adding transcript generation, and a May recap records its one shaping bug: transcripts failed to load because the script's default slug, book, did not match the slug the site used — which is why the slug flag must agree between transcripts and site. The summary_chunks timeline is a July twenty-first addition, implementing the Summary-track request quoted last chapter. One follow-up fix survives verbatim. From the July twenty-first session, prompt twenty-three: "when summary is selected the time shown in the chapters pane is still the running length of the full length chapter. this should be updated when summary is selected." Since that fix, the summary track carries its own durations end to end, and the player shows the summary's own, much shorter length when Summary is selected, not the full chapter's.

Next, build_site.py, the site assembler. It takes the per-chapter audio and its manifest, adds the player, and writes a standalone static site. The current mode is driven by chapters_manifest.json, one entry per chapter; each chapter's id is zero-based, one less than the manifest's chapter number, because it indexes the player's arrays directly. The script copies chapter audio into the site, skipping files already identical by size, and deletes stale audio that no longer belongs.

Two of its details carry sharper provenance. One is the feedback-url flag, which wires in an optional events endpoint and stays off by default. It has a scar: a scrub of private data once dropped the flag's argument-parsing line, and every site build crashed until a July twenty-first commit restored it — a test now pins the flag, which is next chapter's territory. The other is the favicon, verbatim and in two steps. From the July twenty-first session, prompt thirty-one reports "one small bug, no favicon," with a 404 on the icon request. The first fix reused an old icon. Prompt thirty-two corrected it: "no use the favicon from their site, not my old wbt icon," pointing at the Next Chapter program's site. The generator now links the proper icon, and a test pins that too.

Next, luinst. The player is not written in this repository; it is fetched. luinst is a short bash script that shallow-clones landry-ui, a separate component repository, and copies one component into place. Called with a component path and a destination — audiobook slash vanilla into player — it clones into a temporary directory, verifies the component exists, then wipes the destination and copies the component in fresh. The clone address is overridable through an environment variable; the HTTPS form of that override is a durable consequence of the no-SSH machine constraint recorded in a May recap, not a prompt. The fetched player directory is gitignored.

Next, the one-command builder, build_book.sh, in the scripts directory. It wraps the whole Python pipeline so a folder of chapter text files becomes a standalone, emailable player site. It can scaffold a fresh book skeleton or build an existing folder. Staging strips leading numeric ordering prefixes from filenames, and if stripping would collide two chapters it falls back to the original names for all of them. Cache clearing is tiered: a chapter-list change clears the entire chunk cache; one chapter's changed text clears only that chapter's chunks; a changed summary clears only its summary chunks. Before any expensive work it preflights the text-to-speech dependency and auto-fetches the player through luinst if it is absent. It finishes by printing — never running — the command that would zip the site.

The script's purpose is confirmed verbatim. From the July twenty-first session, prompt five asks whether the build book script can produce something "so i can see this in the player locally for testing." Prompt six insists on its defining property: "no, no server, a local only build. a index file i can point my browser at. no running server." The build delivers exactly that, inlining the transcripts as a data URI so an index file opened straight from disk works. And prompt eighteen ties the same standalone build to the publishing workflow.

Then two small servers for local preview: serve.py and serve_chunks.py. serve.py is a threaded HTTP server with byte-range support, answering range requests with a 206 and streaming sixty-four-kilobyte reads. It exists because a page opened from a file path cannot seek audio; the browser needs a real HTTP context. serve_chunks.py publishes a live HLS playlist of chunk WAVs over the local network, marked as an event stream with no end tag so a player keeps re-polling as new chunks appear; it skips files still being written and guards against path traversal. Both are engineering, from April and July commits; no verbatim prompts survive.

Finally, where all of this publishes. There is one target: the parent next-chapter repository's GitHub Pages site. No cloud hosting, no deploy scripts, and the owner does the push. The retarget is verbatim, from the July twenty-first vendoring session, prompt sixteen: "let's replay the commits excluding all personal info and unnecessary info you found (we're not using aws for instance). modify scripts and files as necessary to have it custom tailored to our purposes." Publishing became: copy the per-chapter audio, the manifest, and the transcripts into the parent site's docs folder, and hand the push to the owner.

Every one of these scripts has a test suite and a paper trail. That is the last chapter.
