Last chapter turned sections of prose into audio. This chapter turns that audio into a site you can open and play.

Start with build_transcripts.py. This script produces the read-along you may be watching right now: it lines the words up with the sound. It imports the exact same chunking logic the audio builder uses, so a transcript chunk and its audio are always the same slice of text. For each chapter it re-runs the split into chunks, then walks chunk by chunk, probing the matching WAV file for its duration and recording a start time and an end time rounded to three decimals. The timestamps are chapter-relative: every chapter's first chunk starts at zero. If a chunk's WAV is missing, it prints a warning and stops that chapter early rather than guessing. The output is a single transcripts.json holding books, chapters, and chunks. And when a summary text file exists for a chapter, it emits a second, parallel timeline for that chapter, called summary_chunks, with its own timestamps.

That summary timeline is here because a prompt asked for it. The base alignment feature has no verbatim prompt; it comes from an April commit and a later recap. But the summary_chunks addition traces to the same Summary-track request quoted in the last chapter, from the July twenty-first session. And there is a follow-up fix with a verbatim prompt. From that same session, prompt twenty-three reads: "when summary is selected the time shown in the chapters pane is still the running length of the full length chapter. this should be updated when summary is selected." So the summary track now carries its own durations all the way through, and the player shows the roughly four-minute summary length, not the full chapter length, once you toggle to Summary.

Next, build_site.py. This is the assembler: it takes the per-chapter audio and a manifest, adds the player, and writes out a standalone static site. Its current mode is driven by a chapters manifest, one entry per chapter. A detail worth stating plainly: each chapter's id is zero-based, one less than the manifest's chapter number, because that id indexes the player's arrays directly. The script copies each chapter's audio into the site, skips files that are already identical by size, and removes stale audio that no longer belongs. Cache-busting uses an eight-character content hash of the content itself, rather than a fixed version string, so the version label changes only when the bytes change.

Build_site.py carries two prompt-shaped details worth naming. The first is a flag called dash dash feedback dash url, which wires in an optional events endpoint and is off by default. That flag has a scar: a July twenty-first commit had to restore its argument line, because an earlier scrub of private data had dropped the line and every site build then crashed. The July twenty-first research pass caught that, and there is now a test pinning it, which is next chapter's subject. The second detail is the favicon, and this one is verbatim and iterative. From the July twenty-first session, prompt thirty-one reports "one small bug, no favicon" and a 404 on the icon request. The first fix reused an old icon. Prompt thirty-two corrected it: "no use the favicon from their site, not my old wbt icon," followed by the Next Chapter project's web address. So the site now links a proper icon, pinned by a test.

Next, luinst. The player itself is not written here; it is fetched. Luinst is a small bash script that shallow-clones landry-ui, a component repository, and copies one component into place. You call it with a component path and a destination; it clones into a temporary directory, verifies the component exists, then wipes the destination and copies the component in fresh. It defaults to an HTTPS clone address, a durable consequence of this machine having no SSH git access, recorded in a May recap rather than a standalone prompt. The fetched player directory is gitignored.

Next, the one-command builder: build_book.sh. This wraps the whole Python pipeline so a folder of chapter text files becomes a standalone, emailable player site with no server required. It can scaffold a new book skeleton or build an existing folder. It strips leading numeric ordering prefixes from filenames, and if that stripping would collide two chapters, it falls back to original names for all of them. Its cache handling is tiered: any change to the chapter list clears the whole chunk cache, because the indices shift; a change to one chapter's text clears only that chapter's chunks; a changed summary clears only that chapter's summary chunks. Before doing expensive work it preflights the text-to-speech dependency and auto-fetches the player through luinst if it is missing. It ends by printing, but never running, the command to zip up the site.

The purpose of that script is confirmed verbatim. From the July twenty-first session, prompt five asks whether the build book script can produce something "so i can see this in the player locally for testing." Prompt six is the user insisting on exactly its defining property: "no, no server, a local only build. a index file i can point my browser at. no running server." And prompt eighteen ties that same standalone build to the publishing workflow.

Then two small servers for local preview: serve.py and serve_chunks.py. Serve.py is a threaded HTTP server that adds byte-range support, answering range requests with a 206 and streaming sixty-four-kilobyte reads. It exists because opening the site from a file path can't seek audio; a browser needs a real HTTP context to scrub and to cache. Serve_chunks.py is a companion that publishes a live HLS playlist of chunk WAVs over the local network, marked as an event stream with no end tag so a player keeps re-polling as chunks appear, and it guards against half-written files and path traversal. These are engineering, from April and July commits; no verbatim prompts survive.

Finally, where all this publishes. There is exactly one target: the parent next-chapter repository's GitHub Pages site. No cloud hosting, no deploy scripts, and the owner does the push. The retarget is verbatim, from the July twenty-first vendoring session, prompt sixteen: "let's replay the commits excluding all personal info and unnecessary info you found (we're not using aws for instance). modify scripts and files as necessary to have it custom tailored to our purposes." So publishing became: copy the per-chapter audio, the manifest, and the transcripts into the parent site's docs folder, and let the owner push.

Every one of these scripts has a test suite and a paper trail. That is the last chapter.
