You have heard how repo-story builds an audiobook and how it plays one back. This last chapter is about the proof that the build works and the paper trail that says where this copy came from.

Start with a standing rule. Testing here is not optional and it is not an afterthought. From the July twenty-first session, the prompt is blunt: "you see your directives to test first write code second right?" A later prompt in the same session ties the practice to the written rules: "write it with the prompts and checks we have codified in our rules here." So the tests come first, red before green, and every feature added in the summary-track work of that session shipped with its test in the same commit. There is no continuous-integration server and no pytest configuration anywhere in the repo. The suites are three self-contained scripts, run by hand.

The first is test build book, spelled build underscore book dot s-h, a bash suite of eighteen numbered checks that exercises the staging and preflight logic of build book. It runs without a GPU and without touching the text-to-speech model, by staging only or by putting a stub Python on the path. The checks have teeth. No arguments produces a nonzero exit and a usage message; a nonexistent chapters directory is rejected, and so is an empty one. The happy path asserts real output: chapters sorted, the leading number-dash prefix stripped from each filename, a markdown extension rewritten to text, and the content copied through verbatim. One check changes a single chapter's text and asserts that only that chapter's chunk cache is cleared while its neighbors survive; another adds a chapter to the list and asserts the whole chunk cache clears so the new ordering takes hold. A later check confirms that when the broken Python environment fails to import the chatterbook engine, the build stops early with the remedy printed, before any fetch or synthesis. The final checks cover the summary track end to end: summaries staged beside chapters, a changed summary clearing only its own summary chunks, and build transcripts emitting summary chunks whose first line reads back as "Summary sentence." with a real end timestamp.

The second suite is test build m4a, a Python regression that guards one specific behavior. It generates a silent audio file with ffmpeg, the audio toolkit, then runs build m4a in a temporary directory. It asserts that the summary WAV becomes a file named chapter zero zero zero one dot summary dot m4a, and that the manifest gains a summary block with a plausible duration. Then it does the thing that matters. It changes only the summary track, forces a re-encode, and asserts that the manifest's version hash changes. The docstring states the fear in plain words: cache-busting must key on all content, not just the full tracks. This is the test-first companion to the summary feature from chapter two, pinned so it cannot silently rot.

The third suite is test build site, which guards the manifest-mode site build, and it protects two things that both broke in real life. With no feedback flag given, it asserts the feedback URL does not appear in the page, that the favicon rel-equals-icon link is present, and that the chapter audio is copied. Then it passes a feedback URL and asserts the exact address shows up wired into the page. The docstring names the sharper regression: a prior vendor scrub once dropped the feedback URL's argument definition while the page generator still read it, and every site build crashed. The favicon half is the test-first companion to the favicon fix from chapter three, committed red-green in both suites.

That vendor scrub is the second half of this chapter, and it is where the paper trail lives. This very copy of repo-story is not the original. It is a scrubbed, commit-by-commit replay of a private repository, produced by the script vendor-repo-story and vendored into the parent project on July twenty-first. The reason it is a replay and not a single squashed import comes straight from that session. The prompt reads: "I want to keep as much of the history and files as possible to preserve the cross reference integrity." So each original commit is replayed as its own scrubbed snapshot. The next instruction set the terms: "let's replay the commits excluding all personal info and unnecessary info you found (we're not using aws for instance). modify scripts and files as necessary to have it custom tailored to our purposes."

Every replayed commit carries a trailer in a fixed format: Replayed-From, colon, repo-story, at-sign, the original short hash, then in parentheses, "scrubbed vendor replay." The original author date is preserved; the committer date is the vendoring day, so authorship survives while the re-commit stays honest about when it happened. Excluded from the replay: an Amazon Web Services deploy path the project no longer uses, an undeployed infrastructure blueprint, and personal and machine details, which appear as bracketed placeholders where a value was removed. The script's verify mode re-scans each replayed commit against a banned-token list, because a scrub that misses a single commit is a leak.

The prompts drove one more discipline, the sharpest lesson in the book. Midway through, the author realizes the prompt exports themselves are a leak vector. The prompt: "this does expose that we need to scan our prompts also as a source of private data leakage. I suggest removing them." The correction was immediate and deliberate: "yes, redact, don't delete. go ahead." That single exchange is the origin of the whole project's rule that prompt exports are outward-facing content, scrubbed inline rather than dropped. The prompts you have heard quoted throughout these chapters were themselves cleaned under that policy — family names and infrastructure identifiers redacted inline, the prompts kept whole. Before the leak concerns were closed, they were checked one at a time, enumerated f-one through f-eight, against the vendored source. A separate prompt then called for the README banner that declares this copy the live one and the AWS path retired, and another, weighing a reviewer's limited time over convention, is why the vendored copy keeps only its one live architecture decision record rather than a stack of superseded ones.

The replay is not a claim on paper. The live git log carries twenty-three Replayed-From trailers, one per vendored commit, each naming the private-repo hash it descends from. Commits from the vendoring day forward carry no trailer; they are native to this project. And the chain closes with a person, not a script. The final prompt: "do a final check for personal info on all files in the repo that you will push. if it all checks out, give me the command to flip it public, and i'll push it after that." The scrub, the replay, the inline redaction, the final sweep — and then a human runs the push.

Which closes on a plain fact. This vendored, scrubbed, tested copy is not a museum piece beside the real thing. It is the live pipeline. It is the code that read a repository, wrote the sections, rendered the audio, and built the player for the walkthrough you have just heard.
