After the build and the player, one chapter remains: the proof that the build works, and the paper trail for where this copy of the code came from.

Start with a standing rule. From the July twenty-first session, the prompt is blunt: "you see your directives to test first write code second right?" A later prompt in the same session ties the practice to the written rules: "write it with the prompts and checks we have codified in our rules here." So tests come first, red before green, and every feature in that session's summary-track work shipped with its test in the same commit — one commit grew the bash suite from thirty-three checks to forty-one and added two Python suites. There is no continuous-integration server and no pytest configuration; the suites are self-contained scripts run by hand.

First, test build book — test underscore build underscore book dot s-h — a bash suite covering the staging and preflight logic of build book. It runs without a GPU or the text-to-speech model, using staging-only mode and a stub Python on the path. Bad input fails up front — no arguments, a missing chapters directory, an empty one. The happy path asserts real output: chapters sorted, the leading number-dash prefix stripped, markdown extensions rewritten to text, content copied through verbatim. A broken Python environment that cannot import the chatterbook engine must stop the build early, with the remedy printed. The final checks walk the summary track end to end, down to build transcripts emitting summary chunks with real timestamps.

Next, test build m4a, a Python regression that guards one behavior. Using ffmpeg, the audio toolkit, it generates a silent WAV, runs build m4a in a temporary directory, and asserts that the summary WAV becomes chapter zero zero zero one dot summary dot m4a, with a summary block in the manifest. Then the part that matters: it changes only the summary track, forces a re-encode, and asserts the manifest's version hash changes. The docstring states the fear plainly: cache-busting must key on all content, not just the full tracks. It is the test-first companion to the summary feature.

Third, test build site, guarding the manifest-mode site build against two real regressions. With no feedback flag, it asserts the feedback URL is absent from the page, the favicon rel-equals-icon link is present, and the chapter audio is copied; with a feedback URL passed, the exact address must appear in the page. The docstring names the sharper one: a vendor scrub once dropped the feedback URL's argument definition while the page generator still read it, and every site build crashed. The favicon half is the test-first twin of the favicon fix from chapter three, committed red-green in both suites.

The two newest suites arrived on July thirtieth, alongside the content-addressed chunk cache. Test build audio — test underscore build underscore audio dot p-y — pins the cache-key contract without a GPU. A chunk WAV is identified by what it says and how it is voiced, never by where it sits in the chapter. Same text, voice, and TTS parameters produce the same key; change any one and the key changes. The property that makes incremental regeneration work: editing one sentence changes exactly one key while every other chunk keeps its cache hit, and inserting a sentence shifts every later position but invalidates nothing that follows. Build transcripts must use the same helper, so audio and transcript never disagree about a filename.

Its companion, test chunk cache, guards the maintenance commands in chunk cache dot p-y. It builds a fake book with a legacy index-named cache, runs migrate, and asserts every chunk comes out content-addressed with no index-named file left behind and nothing re-rendered — the file count is unchanged, and a second migrate is idempotent. Then it edits one sentence and runs the orphan sweep, asserting it removes exactly the one chunk the text no longer references while the survivors and the cache-parameters sidecar stay. Its fixture WAVs are deliberately thirty-two-bit float — the format torchaudio writes and Python's wave module refuses to open — because a probe trusting the wave module alone would misread a real cache as empty.

That vendor scrub the site test remembers is the second half of this chapter. This copy of repo-story is not the original. It is a scrubbed, commit-by-commit replay of a private repository, produced by the script vendor-repo-story and vendored into the parent project on July twenty-first. The reason it is a replay, not a squashed import, is in that session's prompt: "I want to keep as much of the history and files as possible to preserve the cross reference integrity." The next instruction set the terms: "let's replay the commits excluding all personal info and unnecessary info you found (we're not using aws for instance). modify scripts and files as necessary to have it custom tailored to our purposes."

Every replayed commit carries a trailer in a fixed format: Replayed-From, colon, repo-story, at-sign, the original short hash, then in parentheses, "scrubbed vendor replay." The original author date is preserved; the committer date is the vendoring day. Excluded from the replay: an Amazon Web Services deploy path the project no longer uses, an undeployed infrastructure blueprint, and personal and machine details, left as bracketed placeholders. The script's verify mode re-scans each replayed commit against a banned-token list, because a scrub that misses one commit is a leak.

The prompts drove one more discipline. Midway through the vendoring, the author realizes the prompt exports themselves are a leak vector. The prompt: "this does expose that we need to scan our prompts also as a source of private data leakage. I suggest removing them." The correction was immediate: "yes, redact, don't delete. go ahead." That exchange is the origin of the project-wide rule that prompt exports are outward-facing content, redacted inline rather than dropped; the prompts quoted throughout these chapters were cleaned under that policy. The enumerated leak concerns, f-one through f-eight, were confirmed resolved against the vendored source. A further prompt called for the README banner declaring this copy the live one and the AWS path retired; another, weighing a reviewer's limited time over convention, pruned the superseded architecture decision records at the flip rather than letting them stack up.

The replay is not a claim on paper. The live git log carries twenty-three Replayed-From trailers, one per vendored commit, each naming the private-repo hash it descends from; commits from the vendoring day forward carry none — they are native to this project. And the chain closes with a person, not a script. Near the end of the July twenty-first session, the prompt: "do a final check for personal info on all files in the repo that you will push. if it all checks out, give me the command to flip it public (the gh command), and i'll push it after that." Scrub, replay, inline redaction, final sweep — then a human runs the push.

One plain fact ends the book. This vendored, scrubbed, tested copy is the live pipeline. It is the code that read a repository, wrote these sections, rendered the audio, and built the player for the walkthrough you have just heard.
