The sections are written. Now build_audio.py gives them a voice.

You run build_audio.py; it finds every section file, orders them, and turns each into spoken audio. Voice comes from a single reference recording: name one with the voice flag, or leave it off and the script checks the voices folder — exactly one wav there is used automatically; two or more, and it stops and asks you to pick; zero, and it stops too. The voice is cloned by Chatterbox, the text-to-speech engine this pipeline runs on. It loads onto a CUDA graphics card, which the script requires, reads the reference recording once to prepare the voice, then reuses that conditioning for every line. Synthesis runs slower than real time, so a full book is a patient job. The final artifact is book dot m4b, tagged with a title and artist you supply.

Almost all of this machinery predates prompt exporting — it arrives in the earliest commits with no prompt to quote — so its provenance is commit messages and one recap, and I'll say when a claim rests on those.

First, chunking. Text-to-speech does not want a whole chapter at once, so the script breaks each section at sentence boundaries — after a period, question mark, or exclamation point — and greedily packs sentences together up to three hundred characters. That limit has no recorded prompt; it has simply been there since the beginning.

After splitting, the code drops any chunk with no word characters at all. A chunk that is nothing but a quotation mark, three dots, another quotation mark carries almost no sound, and fed that, Chatterbox can hallucinate — reading back the transcript of the voice sample it was cloned from instead. A voice-sample leak. The fix, from July third, is recorded in a commit message and an in-code comment, not a verbatim prompt: drop those chunks before synthesis. Dropping a chunk shifts every later chunk's position — a shift that once poisoned the cache. The next feature is why it no longer does.

Synthesis is expensive, so every chunk is saved to disk, and the cache is content-addressed. Each chunk's filename carries its chapter number, its track variant, and twelve characters of a hash over the chunk's exact text, the voice file's name, and the sampling parameters. Position is deliberately not in the key. Edit one sentence and only the chunks it touches get new names and re-render; every other chunk, though the edit shifted its position, keeps its name and stays a cache hit. Re-run the script and every chunk whose file exists prints cached, skipping. This replaced a scheme that named chunks by index, where any edit shifted the numbering and silently paired old audio with new positions; the only safe response was re-rendering the whole book. The script also writes cache params dot j-son, recording the voice and parameters the cache was keyed with, so the transcript builder can recompute the names without loading the model. Each chunk goes to a temporary file, then is renamed into place, so a kill mid-write can't leave a corrupt chunk.

A companion script, chunk_cache.py, maintains that cache. Its migrate command renames a legacy index-named cache into content addressing without re-rendering anything — valid only while the text is unchanged since that render, because the rename asserts the old positions still match. Its gc command deletes chunk wavs the current text no longer references. This content addressing is the newest work here, from July thirtieth; the decision record that moves narration onto a dedicated writing model leans on it — content addressing makes re-narrating a chapter affordable.

Once a chapter's chunks exist, ffmpeg — the media tool this pipeline shells out to — concatenates them into one chapter wav, and the assembly step stitches the chapter wavs into the single book dot m4b, writing each chapter's start and end time so a player can jump between chapters. The final encode is A-A-C at one hundred twenty-eight kilobits, plus fast start for playback before the full download. Whatever title you pass, the album tag is always Repo Story, hardcoded. The July second work that set this metadata survives only in the project's done list, not a saved prompt.

Next, build_m4a.py — and here the format changes for a reason. This is the production format: the web player consumes one m4a file per chapter, listed in a manifest, not a single book file; book dot m4b became the standalone, legacy artifact. The switch traces to the May twenty-second recap, which records the cause as a diagnosis, not a prompt: the deployed player had moved to a per-chapter model, and a restart-chapter bug surfaced because this pipeline still produced one file. So build_m4a.py re-encodes each chapter wav to its own m4a — sixty-four kilobits, twenty-four thousand hertz, mono — named chapter, four digits, dot m4a, and writes chapters manifest dot j-son, listing each chapter's title, duration, and size. The manifest's version is a content hash, the first eight characters of a hash over each chapter's filename, size, and duration; change the audio and the version changes, so the player knows to reload. A missing m4a gets a printed warning and is skipped rather than failing the run. There was no prompt for this switch. It was diagnosed in a browser.

Now the one feature here with rich, verbatim provenance: the Full and Summary track split, from the July twenty-first session. It begins with a worry about reviewer time. The prompt reads: I like how this tells a story, and it is enjoyable to listen to, but I fear the reviewer won't spend the time on it due to the workload they have. It asks for two buttons beside the transcript label — Full and Summary — so a listener can hear a condensed version and, in the user's words, not have to spend the huge time investment for the arc if they only want the pertinent details.

The user gated the work. A second prompt that same day: don't do anything yet except generate the summary and show it to me. Only after approving a sample did the third prompt land the feature, and its wording set the shape of the pipeline. The summary is good. Incorporate the UI needed to flip between the summary and full text. Add the summary text as the final step of generating a chapter.

The final step of generating a chapter. That phrase is why the summary pass sits right after the full-audio pass in the chapter loop, not off in a separate stage. In build_audio.py, a summaries folder triggers a second synthesis run per chapter, cached under its own summary variant and concatenated to a wav whose summary name keeps it out of the M4B and out of build_m4a's chapter glob — summaries never enter the book file. In build_m4a.py those summary wavs become their own summary m4a files, each chapter in the manifest gains a summary block, and the version hash folds the summaries in, so a summary-only change still busts the cache.

Audio alone isn't the product. For the site to play any of this, it needs transcripts and a manifest that ties the words to the sound.
