The sections are written. Now build_audio.py gives them a voice.

Start with the command. You run build_audio.py, and it finds every section file, orders them, and turns each one into spoken audio. Voice comes from a single reference recording. Pass the voice flag and it uses that file; leave it off and the script looks in the voices folder, and when exactly one wav sits there, uses it automatically. Two or more, and it stops, prints the names, and tells you to specify one. Zero, and it stops too. The voice itself is cloned by Chatterbox, the text-to-speech engine this pipeline runs on. It loads onto a CUDA graphics card, which the script requires, reads the reference recording once to prepare the voice, then reuses that for every line it speaks. Synthesis runs slower than real time, so a full book is a patient job. The final artifact is book dot m4b, tagged with a title and artist you supply, though the album tag is always the same two words: Repo Story.

Almost all of this machinery predates prompt exporting in this project. The chunking, the voice cloning, the encoding arrive in the earliest commits with no prompt to quote. So for this stretch the provenance is commit messages and one recap, and I'll say plainly when a claim rests on those rather than a recorded instruction. Where I describe what a commit records, that is paraphrase or inference, not a quote.

Consider the chunking. Text-to-speech does not want a whole chapter at once, so the script breaks each section at sentence boundaries — after a period, question mark, or exclamation point — and greedily packs sentences together up to three hundred characters. That three-hundred limit has no recorded prompt; it has simply been there since the beginning.

Then comes a filter with a real reason behind it. After splitting, the code drops any chunk that contains no word characters at all. Picture a chunk that is nothing but a quotation mark, three dots, another quotation mark. It carries almost no sound. Fed that, Chatterbox can hallucinate — instead of reading the near-empty text, it reads back the transcript of the voice sample it was cloned from. A voice-sample leak. The fix, from the July third session, is recorded in the commit message and an in-code comment, not a verbatim prompt: drop the word-character-free chunks before synthesis. The comment also flags a consequence you have to respect. Dropping a chunk shifts the numbering of every chunk after it in that section, so if you change the filter you must clear that section's cached audio before regenerating, or the cache and the text fall out of step.

That cache is the next feature. Synthesis is expensive, so every chunk is saved to disk under a name built from its chapter number and its position — chapter zero one, chunk zero zero zero zero three, and so on. Re-run the script and, for every chunk whose file already exists, it prints cached, skipping, and moves on. A long run that dies halfway resumes almost where it stopped. And each chunk is written safely: the audio goes to a temporary file first, then gets renamed into place, so a process killed mid-write can never leave a corrupt chunk behind.

Once a chapter's chunks exist, ffmpeg — the media tool this pipeline shells out to — concatenates them into one chapter wav. Then the assembly step stitches the chapter wavs into the single book dot m4b, writing a chapter marker for each with its start and end time so a player can jump between chapters. The final encode is A-A-C at one hundred twenty-eight kilobits, with fast start so playback can begin before the whole file downloads. One detail is deliberately fixed: whatever title you pass, the album tag is always Repo Story, hardcoded. The July second work that set this metadata survives only as an entry in the project's done list, not as a saved prompt.

Next, build_m4a.py — and here the format changes for a reason. This is the production format. The web player consumes one m4a file per chapter, listed in a manifest, not a single book file; that book dot m4b became the standalone, legacy artifact. The switch traces to the May twenty-second recap, which records the cause as a diagnosis, not a prompt: the deployed player had moved to a per-chapter model, and a restart-chapter bug surfaced because this pipeline was still producing one monolithic file. So build_m4a.py re-encodes each chapter wav to its own m4a — this time at sixty-four kilobits, twenty-four thousand hertz, mono, lighter than the book file — named chapter, four digits, dot m4a. Alongside them it writes chapters manifest dot j-son, listing every chapter with its title, duration, and size. The manifest's version is not a fixed label; it is a content hash, the first eight characters of a hash over each chapter's filename, size, and duration. Change the audio and the version changes, and the player knows to reload. A chapter whose m4a is missing gets a printed warning and is skipped rather than failing the run. There was no prompt for this switch. It was diagnosed in a browser.

Which brings us to the one feature in this chapter with rich, verbatim provenance: the Full and Summary track split. It comes from the July twenty-first session, and it begins with a worry about the reviewer's time. The prompt reads: I like how this tells a story, and it is enjoyable to listen to, but I fear the reviewer won't spend the time on it due to the workload they have. It asks for two buttons beside the transcript label — Full and Summary — so a listener can hear a condensed version and, in the user's words, not have to spend the huge time investment for the arc if they only want the pertinent details.

The user gated the work. A second prompt that same day: don't do anything yet except generate the summary and show it to me. Only after approving a sample did the third prompt land the feature, and its wording set the shape of the whole pipeline. The summary is good. Incorporate the UI needed to flip between the summary and full text — add the summary text as the final step of generating a chapter.

The final step of generating a chapter. That phrase is why the summary pass sits right after the full-audio pass in the chapter loop, not off in a separate stage. In build_audio.py, a summaries folder triggers a second synthesis run per chapter, cached under its own summary prefix and concatenated to a wav whose summary name deliberately keeps it out of the M4B and out of build_m4a's chapter glob — summaries never enter the book file. In build_m4a.py those summary wavs become their own summary m4a files, and each chapter in the manifest gains a summary block. The version hash even folds the summaries in, so a summary-only change still busts the cache.

Audio alone isn't the product. For the site to play any of this, it needs transcripts and a manifest that ties the words to the sound.
